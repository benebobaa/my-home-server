# 0010 — One shared PostgreSQL 18 for the lab's apps; the app standard

**Status:** accepted (2026-10-10)

## Context

Apps are next (README: "Databases → apps"), and most of them need a
relational database. Before the first one arrives, the lab needs an answer to
"where does an app's data live, how does it get its credentials, how is it
backed up and watched". Without one, every app invents its own and the lab
ends up with N databases on N disks, each backed up (or not) its own way.

What was in place (2026-10-10):

- The observability standard (ADR 0008) and nightly PBS backups of every
  guest (ADR 0009).
- `lab.yaml` already reserved `postgres` at `10.10.20.21` on pve2 (VLAN 20),
  and the hEX already had the pinhole for Kubeletto's K3s VM to it.
- pve2: 12 GB RAM (~9 GB free), thin pool 71 % used. The single operator.

Options considered:

- **A Postgres per app (in its own container, or bundled):** isolation, but
  N instances to size, patch, back up and watch, and each one idle-heavy on a
  12 GB node.
- **Postgres inside each app's container:** the same, plus the database
  dies with an app rebuild.
- **One shared instance, a database + role per app:** one thing to patch,
  back up, dump and watch; isolation by role and `pg_hba`. A noisy app can
  slow the others: acceptable at homelab scale, revisited if it happens.

Version: PostgreSQL 18 is the current major (18.6, 2026-08-13; supported
until 2030-11). 19 is not released. Debian 13 ships 17, so the packages
come from the PostgreSQL project's own repo (PGDG).

## Decision

**One shared PostgreSQL 18, CT 130 `postgres` on pve2, VLAN 20**
(`10.10.20.21`, `postgres.home.arpa`), from PGDG, major pinned, minor
releases from the repo.

- **One database and one login role per app, both named after the app.**
  `pg_hba` admits apps only from VLAN 20, only over TLS, only by password
  (scram-sha-256), and only to the database named after their role
  (`sameuser`). PUBLIC has no rights on app databases.
- **Passwords are generated by OpenTofu** (`random_password`, encrypted
  state), sent to the CT and to the app's guest over the pinned root SSH.
  No operator ever types one; rotation is one `-replace`.
- **Nothing is dropped automatically.** Removing an app from `postgres.tf`
  leaves its database; dropping it is a deliberate hand step (destructive).
- **Backups are two layers.** The nightly PBS snapshot of the CT
  (crash-consistent: Postgres recovers it like a power cut) plus a logical
  dump at 01:30, `pg_dumpall --globals-only` and one `pg_dump -Fc` per
  database, written to the CT's disk so the 02:30 backup carries it. The dump
  restores one app's database without touching the others, and across major
  versions.
- **Logs go to the journal** (`log_destination = syslog`), so they ship to
  VictoriaLogs like everything else; statements are never logged in full.
- **Databases get an exporter.** This changes the observability standard:
  "don't add an exporter just for metrics" stays the rule for apps, but a
  database has no HTTP health URL and its failure modes (down, disk full,
  connections exhausted) are invisible from the Proxmox API.
  `postgres_exporter` connects over the unix socket by peer auth (no
  password); its `pg_up` is the health check. Alerts: `app-postgres.yml`.
- **Tier `standard` until an app depends on it,** then `critical`.

**The app standard** (`docs/standards/apps.md`) records the rest of the
contract for any app: state on the guest's own volume, secrets from the repo
(SOPS or generated) through the pinned SSH and never in the image or the
repo in plain text, a database from the shared instance, reachable over
Tailscale by default and publicly only through Cloudflare Tunnel (ADR 0004).
What an app runs *on* (a container per app vs a shared Docker/K3s host) is
deliberately left open for the Kubeletto session.

## Consequences

- A dump failure is visible only in the journal (the unit fails; logs in
  VictoriaLogs): no metric reaches Prometheus from inside the CT. The PBS
  snapshot still covers the database. Add a freshness check if that gap ever
  bites — the same position ADR 0009 takes on backup age.
- The shared instance is a single point of failure for every app that uses
  it. When the first app depends on it, its tier goes to `critical`.
- Kubeletto's K3s VM (DMZ) needs a `pg_hba` line for its address when it is
  built; the hEX pinhole already exists.
- A new major (19) is a `pg_upgradecluster`, planned and tested on a
  restored copy first, never a re-run of `setup.sh`.
- The root disk holds data, WAL and the last 3 dumps: `PostgresDiskFilling`
  fires at 80 %; grow the disk in place.
