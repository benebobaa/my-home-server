# 0016 — Shared NATS (JetStream) and Valkey for the lab's apps

**Status:** accepted (2026-10-14)

## Context

ADR 0010 gave apps one shared Postgres. Apps also need a message bus and a
cache, and the only ones in the lab today sit inside Kubeletto's K3s server
VM (in the DMZ): an in-cluster NATS with JetStream (12 streams, 6.3 GB
reserved, about 1 MB used) and a memory-only Valkey with no password. The
operator asked for these as lab services that any app can share, like the
database (2026-10-14).

What was in place (2026-10-14):

- pve2: about 3.3 GB of RAM available and the lab's tightest CPU (load ~3 on
  4 threads). pve3: about 1.4 GB available. No new hardware (budget).
- VLAN 20 (`servers`) is trunked to both nodes; Postgres is CT 130 there.
- Kubeletto's untrusted clients (build pods, the log shipper on the worker
  VM) connect to its NATS with restricted users. Kubeletto's code does not
  prefix its Valkey keys.

Checked before deciding:

- A NATS leaf node **without** JetStream does not see the hub's JetStream by
  default ("no responders"). With a JetStream domain on the hub (`hub`) and a
  subject mapping on the leaf (`$JS.API.>` to `$JS.hub.API.>`), clients of
  the leaf create streams, publish with acks and consume as if JetStream were
  local, with no client change (tested with nats-server 2.15.0: 13 streams of
  500 MB through the leaf, a restricted user's acked publish, a consumer).
- Debian 13 ships Valkey 8.1 with a `valkey-server@.service` template, so one
  process per app is a packaged pattern.
- go-redis accepts `rediss://…?skip_verify=true`, so a TLS-only Valkey needs
  no client code change.

## Decision

**Shared NATS: CT 131 `nats` on pve2, VLAN 20** (`10.10.20.22`,
`nats.home.arpa`). It holds state (JetStream), so pve2.

- nats-server pinned upstream release (sha256-verified; Debian has none),
  JetStream domain `hub`, file store on the CT's own disk.
- **One account per app,** with the app's JetStream limits, and the app's
  users inside it. Passwords are generated by OpenTofu, and the config holds
  only their bcrypt hashes. Accounts cannot see each other's subjects or
  streams.
- **TLS on the client (4222) and leaf (7422) listeners** with a self-signed
  certificate that OpenTofu generates with the hub's name and IP (so it
  survives a rebuild of the CT). Clients **pin** it (a leaf's `ca_file`,
  output `nats_tls_cert`); a client library that cannot load a certificate
  may only skip verification, the Postgres `sslmode=require` stance. The
  monitoring port (8222) is plain HTTP for the health probe and
  `prometheus-nats-exporter` (7777).
- **Apps outside VLAN 20 run a leaf node of their own** (stateless, no
  JetStream, the mapping above). Only the leaf's host gets an exact hEX rule
  to 7422, and the app's untrusted clients stay on its leaf with their
  restricted users. Kubeletto is the case this exists for: its leaf runs on
  the K3s server VM, never the worker.

**Shared Valkey: CT 132 `valkey` on pve3, VLAN 20** (`10.10.20.23`,
`valkey.home.arpa`). A cache holds nothing to back up, so pve3, which keeps
pve2's CPU for the stateful guests.

- **One Valkey process per app** (`valkey-server@<app>`), each with its own
  port (from 6380), password and `maxmemory`. Not one shared keyspace with ACL
  key patterns: that needs every app to prefix its keys (Kubeletto does not),
  and one shared `maxmemory` lets a noisy app evict the others' keys.
- **TLS only** (no plaintext port), the CT's own self-signed certificate,
  not verified by clients: go-redis takes no certificate from a URL, so
  pinning would need code in each app. Debian's package, so security fixes
  come with `apt`.
- **No persistence.** A cache by definition: what must survive a restart
  belongs in Postgres or in a JetStream stream.
- One `redis_exporter` per instance (9121, 9122, …), over the instance's unix
  socket.

**Both:** `monitoring:` blocks per the observability standard, journal to
`logs`, PBS nightly like every guest, tier `standard` until an app depends on
them. The app standard (`docs/standards/apps.md`) gains how an app gets an
account and an instance.

**Kubeletto moves onto them after the cutover's 24-hour check**, not on the
day the services are built: its in-cluster NATS becomes a leaf of the hub
(its streams are recreated by core at startup), and its `REDIS_URL` points at
its instance. The two hEX rules (K3s server VM to 7422 and to its Valkey
port) come with that change, by runbook.

**Not shared yet:** object storage, a registry, package mirrors. Each the day
a second app needs it. Never: heavy stacks (Kafka, Keycloak, Nexus) on these
nodes.

## Consequences

- The hub is a single point of failure for every app's messaging. A leaf
  that loses the hub keeps local core NATS working, but JetStream calls fail
  until it is back; Kubeletto's outbox lives in Postgres and republishes.
- JetStream reservations count against the account and the server, not the
  disk: Kubeletto's 12 streams reserve 6.3 GB while using ~1 MB, so its
  account allows 8 GB and the server 10 GB on a 16 GB thin-provisioned disk.
- A Valkey restart empties every app's cache at once. Apps must tolerate
  that (Kubeletto's locks and rate limits do).
- Two more DMZ-to-servers rules once Kubeletto moves, each from one address
  to one port.
- Valkey's TLS is not verified by its clients: it stops passive reading on
  the wire, not an active man in the middle on the router path (which would
  need the router itself). NATS's leaf link, the one that crosses from the
  DMZ, is pinned.
