# 0017 — Valkey clients pin its certificate

**Status:** accepted (2026-10-15). Supersedes ADR 0016's Valkey TLS stance
("not verified by clients"); the rest of 0016 stands.

## Context

ADR 0016 made the shared Valkey TLS only with the CT's own self-signed
certificate, and left clients to skip verification (`?skip_verify=true`)
because go-redis takes no certificate from a URL. A security review of the
switch preparation (2026-10-15) flagged it: Kubeletto's core would reach
Valkey from the DMZ through the hEX unverified, so anyone in the path could
read and change its locks and rate limits. The NATS leaf link was already
pinned (0016).

## Decision

- **Valkey's certificate is generated by OpenTofu** (`tls_self_signed_cert.valkey`:
  `valkey.home.arpa` and the CT's IP, 10 years), like the NATS hub's, so it
  survives a rebuild. Output `valkey_tls_cert`.
- **Clients pin it.** Kubeletto's core gained `REDIS_TLS_CA` (PEM): with it,
  a `rediss://` server is verified against that certificate instead of the
  system roots, and the URL carries no `skip_verify` (core refuses both
  together). Other apps do the same with their client's CA option.

## Consequences

- Verified end to end on 2026-10-15 from VLAN 20 with go-redis: pinned
  connects, unpinned is refused (unknown authority).
- Replacing the certificate (a `-replace`, or its 10-year expiry) means
  re-delivering it to every client, and restarts the instances (their cache
  empties).
- Nothing on the lab path is left unverified: Postgres's `sslmode=require`
  remains the one exception, and only inside the servers VLAN or through its
  pinhole.
